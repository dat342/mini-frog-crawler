CLAUDE:
Câu hỏi hay! Crawl dữ liệu web (như Screaming Frog hay Googlebot) dựa trên một số nguyên tắc và kỹ thuật cốt lõi sau:

## 1. Nguyên tắc hoạt động cơ bản — "Crawl theo đồ thị liên kết"

Website về bản chất là một **đồ thị (graph)**: mỗi trang là một node, mỗi link là một cạnh. Crawler hoạt động theo vòng lặp:

```
1. Bắt đầu từ URL gốc (seed URL, ví dụ: homepage)
2. Tải HTML của trang đó về (HTTP request)
3. Phân tích (parse) HTML → trích xuất dữ liệu + tìm tất cả link <a href>
4. Đưa các link mới tìm được vào hàng đợi (URL queue/frontier)
5. Lấy URL tiếp theo từ hàng đợi → quay lại bước 2
6. Lặp đến khi hết URL hoặc đạt giới hạn
```

Thuật toán duyệt thường là **BFS (Breadth-First Search)** — quét hết trang cùng độ sâu trước rồi mới đi sâu hơn. Đây là lý do Screaming Frog có cột "Crawl Depth" (số click từ homepage đến trang đó).

## 2. Các kỹ thuật chính

**HTTP Request/Response**
- Gửi request với `User-Agent` riêng (ví dụ `Screaming Frog SEO Spider`) — server biết ai đang crawl
- Đọc **status code** (200, 301, 404, 503...), **response headers** (content-type, canonical header, cache...)
- Đo thời gian phản hồi (response time)

**HTML Parsing**
- Dùng parser để đọc cây DOM, trích xuất: `<title>`, `<meta>`, `<h1>-<h6>`, `<a href>`, `<img alt>`, canonical, hreflang, schema markup...
- Đây là crawl "raw HTML" — nhanh nhưng không thấy nội dung do JavaScript sinh ra

**JavaScript Rendering** (kỹ thuật nâng cao)
- Với site dùng React/Vue/Angular, HTML gốc gần như rỗng
- Crawler phải nhúng **headless browser** (Screaming Frog dùng Chromium) để chạy JS, chờ trang render xong rồi mới đọc DOM cuối cùng
- Chậm và tốn tài nguyên hơn nhiều so với crawl HTML thuần

**Chuẩn hóa & khử trùng lặp URL (URL Normalization / Deduplication)**
- `example.com/page`, `example.com/page/`, `example.com/page?utm=x` có thể là cùng một trang
- Crawler phải chuẩn hóa URL và lưu danh sách "đã crawl" (thường dùng hash set) để không quét lặp vô hạn

## 3. Nguyên tắc "lịch sự" (Politeness) — rất quan trọng

Crawler tử tế phải tuân thủ:

- **robots.txt**: đọc file này *trước tiên* để biết chỗ nào được phép/cấm crawl (`Disallow`, `Allow`)
- **Meta robots / X-Robots-Tag**: tôn trọng `noindex`, `nofollow` trên từng trang
- **Rate limiting / Crawl delay**: giới hạn số request/giây để không đè sập server người ta (Screaming Frog cho chỉnh "Max Threads" và "Speed")
- **Crawl budget**: giới hạn tổng số URL, độ sâu tối đa

## 4. Các nguồn dữ liệu bổ trợ

Ngoài đi theo link, crawler còn khám phá URL qua:
- **XML Sitemap** — danh sách URL chủ website tự khai báo
- **API bên ngoài** — Screaming Frog nối với Search Console, Analytics, PageSpeed để đối chiếu URL thực tế có traffic với URL crawl được (tìm ra "orphan pages" — trang không có link nội bộ trỏ tới)

## Tóm gọn

| Tầng | Kỹ thuật |
|---|---|
| Khám phá URL | Duyệt đồ thị link (BFS), sitemap, queue |
| Lấy dữ liệu | HTTP request, đọc status/headers |
| Trích xuất | HTML parsing (DOM), JS rendering (headless browser) |
| Kiểm soát | robots.txt, rate limit, dedup URL, crawl depth |

Googlebot cũng hoạt động trên đúng các nguyên tắc này, chỉ khác ở quy mô (phân tán hàng nghìn máy) và có thêm tầng lập chỉ mục (indexing) + xếp hạng (ranking) phía sau. Screaming Frog thực chất là "mô phỏng Googlebot thu nhỏ" chạy trên máy bạn — vì vậy nó giúp bạn nhìn website *theo cách Google nhìn*.

Bạn muốn đào sâu phần nào — ví dụ cách xử lý JavaScript rendering, hay cách phát hiện duplicate content?

| Tính năng Screaming Frog | Trên GitHub Actions |

## Những gì bị giới hạn (~40–60%)

- **Quy mô crawl**: Runner free có **2 CPU / 7GB RAM / 6 giờ tối đa mỗi job**. Crawl HTML thuần thì 50.000–200.000 URL vẫn ổn, nhưng nếu bật JS rendering thì tụt xuống còn vài nghìn URL (mỗi trang render mất 2–5 giây).
- **Không có database bền vững**: Screaming Frog lưu crawl vào disk database. Trên Actions bạn phải tự lưu kết quả ra artifact/repo/S3 mỗi lần chạy.
- **Free tier**: 2.000 phút/tháng cho repo private (repo public thì không giới hạn) — crawl lớn thường xuyên sẽ hết quota.

## Những gì gần như không làm được (~0%)

- **Giao diện GUI tương tác**: xem crawl real-time, click vào URL xem inlinks/outlinks, visualize crawl tree dạng đồ họa. Đây là ~30% giá trị của Screaming Frog với người dùng phổ thông. Bù được một phần bằng cách xuất **báo cáo HTML tĩnh** đẩy lên GitHub Pages — xem được nhưng không tương tác trực tiếp với crawl đang chạy.
- **Pause/resume crawl giữa chừng bằng tay**, điều chỉnh cấu hình khi đang crawl.

## Kết luận theo mục đích sử dụng

- **Audit SEO tự động, định kỳ, xuất báo cáo** → đáp ứng ~90%, thậm chí tiện hơn Screaming Frog vì chạy tự động không cần mở máy
- **Thay thế hoàn toàn trải nghiệm Screaming Frog** (GUI, khám phá tương tác) → chỉ ~50–60%
- **Crawl site rất lớn (500k+ URL) có JS rendering** → không phù hợp, nên thuê VPS thay vì Actions

Kiến trúc gợi ý nếu bạn làm: **GitHub Actions (cron) → script crawl (Scrapy hoặc crawlee) → xuất CSV + báo cáo HTML → commit vào repo / đẩy lên GitHub Pages → gửi thông báo qua Telegram/email khi phát hiện lỗi mới**.

Nếu bạn muốn bắt đầu, mình có thể dựng khung project này cho bạn — bạn định crawl site cỡ bao nhiêu URL và có cần JS rendering không?

- Pattern phân loại trang đã cài sẵn cho URL tiếng Việt (`/danh-muc`, `/san-pham`, `/tin-tuc`...) — sửa được trong mục ⚙ trước khi crawl

- Tôn trọng robots.txt, không dùng API nào, chạy 100% miễn phí

Câu hỏi hay — "Luồng song song" (concurrency) là **số request được gửi đồng thời đến website** tại một thời điểm. Trong tool của bạn, nó hoạt động thế này:

## Cơ chế bên trong

Tool tạo ra N "worker" chạy song song (mặc định 5). Mỗi worker liên tục: lấy 1 URL từ hàng đợi → gửi request → chờ phản hồi → bóc tách → lấy URL tiếp theo. Về kỹ thuật, đây là **async I/O** chứ không phải thread thật — trong lúc worker A đang *chờ* website phản hồi (thường 200–800ms), worker B, C, D, E tranh thủ gửi request của mình. Nhờ vậy 5 luồng nhanh gần gấp 5 lần 1 luồng, mà máy bạn gần như không tốn thêm CPU.

Ngoài ra mỗi worker còn nghỉ 0,2 giây giữa 2 request (delay) — nên tốc độ thực tế tối đa khoảng: `5 luồng ÷ 0,2s ≈ tối đa ~25 request/giây` (thực tế thấp hơn vì còn chờ server phản hồi).

## Chọn số luồng dựa trên 3 yếu tố

**1. Sức chịu tải của website bị crawl — yếu tố quan trọng nhất**
Mỗi request của bạn là một khách truy cập "ảo". Website nhỏ chạy hosting giá rẻ mà bạn bắn 10 luồng liên tục có thể bị chậm hẳn đi, thậm chí sập — điều này vừa thiếu tôn trọng vừa làm sai lệch số đo response time của chính bạn.

**2. Nguy cơ bị chặn (rate limiting / firewall)**
Nhiều site dùng Cloudflare, firewall hosting... sẽ phát hiện "1 IP gửi quá nhiều request/giây" và trả về lỗi **429 (Too Many Requests)** hoặc **403**, hoặc chặn hẳn IP của bạn. Crawl càng nhanh → càng dễ bị nhận diện là bot tấn công. Đây là lý do Screaming Frog cũng mặc định chỉ 5 threads.

**3. Tốc độ mạng và độ trễ của server**
Server phản hồi chậm (500ms+) thì tăng luồng giúp bù thời gian chờ. Server phản hồi nhanh (dưới 100ms) thì 3–5 luồng đã đủ nhanh, tăng thêm chỉ tăng rủi ro bị chặn.

## Gợi ý thực tế

| Tình huống | Số luồng nên dùng |
|---|---|
| Site nhỏ, hosting yếu, không rõ hạ tầng | **2–3** |
| Đa số website VN thông thường | **5** (mặc định — cân bằng tốt) |
| Site lớn hạ tầng mạnh (sàn TMĐT, hosting xịn) | 8–10 |
| **Website của chính bạn**, crawl ngoài giờ cao điểm | 10 (tool giới hạn max 10) |

Dấu hiệu bạn đặt quá cao: cột **Status** xuất hiện nhiều lỗi 429/403/timeout, hoặc **Phản hồi (ms)** tăng vọt so với lúc đầu crawl. Gặp vậy thì giảm luồng xuống và crawl lại.

Quy tắc chung: **crawl chậm mà xong, hơn crawl nhanh mà bị chặn giữa chừng** — nhất là khi bạn quét site của khách hàng hoặc đối thủ.

- **Near-duplicate content**: SF phát hiện cả trang *gần giống nhau* (thuật toán simhash), tool bạn mới bắt trùng title/meta *y hệt*
- **Hreflang** — quan trọng nếu site đa ngôn ngữ (như ILA có `/en/`)
- **Structured data / Schema.org**: SF phát hiện và validate; tool bạn chưa đọc
- **Word count / độ dài nội dung** mỗi trang — lọc trang mỏng (thin content)
- **X-Robots-Tag trong HTTP header** (noindex đặt ở header thay vì meta tag — tool bạn sẽ bỏ sót)
- **Custom extraction**: SF cho bóc bất kỳ dữ liệu nào bằng XPath/CSS selector (giá sản phẩm, SKU, ngày đăng...)
- **Include/Exclude regex**: loại trừ URL theo mẫu trước khi crawl (vd bỏ `?sort=`, `/tag/`)
- **Crawl site cần đăng nhập** (HTTP auth, cookies, form login)

## Nhóm 3 — Thiếu nhưng khó/không đáng làm lại

- **Quy mô**: SF bản trả phí crawl hàng triệu URL nhờ lưu disk; tool bạn giữ trong RAM, thực tế thoải mái đến ~5.000–10.000 URL
- **Visualization**: sơ đồ cây crawl, force-directed graph
- **Hệ sinh thái tích hợp**: GA4, GSC, PageSpeed (bạn chủ động bỏ), Looker Studio
- **Tạo XML sitemap**, kiểm tra chính tả, AMP audit...

## Ngược lại, tool của bạn có thứ Screaming Frog không có

- Miễn phí không giới hạn 500 URL như bản free của SF (SF trả phí ~£259/năm)
- **Phân tầng danh mục/sản phẩm theo cây URL tự động** — SF chỉ hiện folder depth, không suy luận cha–con thành loại trang


## Lưu ý trung thực về giới hạn

- Site **không khai báo gì** (không meta date, không schema, không sitemap) thì ô sẽ trống — không tool nào bịa ra được, kể cả Screaming Frog. Ví dụ hoptrisummit.com không có sitemap, nên trang nào không nhúng schema sẽ trống cả 2 cột.
- "Ngày tối ưu" (dateModified/lastmod) là **ngày site tự khai**, có site khai không trung thực (tự động cập nhật lastmod hằng ngày để "lừa" Google) — nếu thấy cả nghìn trang cùng ngày cập nhật giống hệt nhau thì nên nghi ngờ.

**Inlinks = số liên kết nội bộ trỏ ĐẾN trang đó**, đếm từ các trang đã crawl trong cùng website.

## Ví dụ cụ thể

Giả sử tool crawl 60 trang của hoptrisummit.com:

```
Trang A ──link──→ /san-pham/abate-1sg
Trang B ──link──→ /san-pham/abate-1sg      → abate-1sg có 3 inlinks
Trang C ──link──→ /san-pham/abate-1sg
```

Cách đếm trong tool: mỗi trang nguồn chỉ tính 1 lần cho mỗi đích (trang A có 5 chỗ cùng link tới abate-1sg thì vẫn đếm 1). Vì vậy **inlinks ≈ số trang có link trỏ tới trang đó**.

Đó là lý do lúc test bạn thấy trang chủ và các mục menu có đúng **60 inlinks khi crawl 60 trang** — logo và menu xuất hiện trên mọi trang, nên trang nào cũng "bỏ phiếu" cho chúng.

## Vì sao chỉ số này quan trọng với SEO

- **Inlinks nhiều** = site đang "nói" với Google rằng trang này quan trọng (link equity nội bộ chảy về nhiều). Trang chủ, danh mục lớn luôn cao là bình thường.
- **Inlinks ít (1–2)** = trang nằm sâu, Google ít ghé, khó có thứ hạng tốt. Đáng chú ý nhất là **trang sản phẩm/bài viết quan trọng mà inlinks thấp** → cần đi thêm link nội bộ về nó.
- **Inlinks = 0** = trang không ai trỏ tới, chỉ được tìm thấy qua đường khác (bộ lọc "Không có inlink" trong tool). Họ hàng với **orphan pages** — khác ở chỗ orphan là "có trong sitemap nhưng crawl không hề gặp".
- **Anchor text** kèm theo (bấm vào dòng để xem) cho biết các trang khác đang dùng cụm từ gì để trỏ về — Google dùng anchor để hiểu trang đích nói về chủ đề gì. Anchor toàn "xem thêm", "click vào đây" là phí cơ hội SEO.

Một mẹo dùng thực tế: sort cột Inlinks tăng dần trong Excel (sheet URLs), lọc ra các trang sản phẩm chủ lực có inlinks < 5 — đó chính là danh sách cần bổ sung link nội bộ từ bài blog liên quan.

# Trả lời: Có — Wayback Machine, và đã tích hợp vào tool

## Phương án khả thi duy nhất để "khảo cổ" ngày

**Wayback Machine (web.archive.org)** — kho lưu trữ web từ 1996, chụp lại các trang web định kỳ:
- **Bản chụp đầu tiên** của URL → "trang này tồn tại muộn nhất từ ngày X" (cận trên của ngày đăng thật)
- **Bản chụp cuối** → lần cuối trang được ghi nhận còn sống

Các phương án khác đều không tự động hóa được: Google `before:/after:` bị chặn bot, RSS chỉ giữ bài mới, ngày trong URL thì ít site VN dùng.

## Đã thêm vào tool (checkbox trong mục ⚙ nâng cao)

**"Tra Wayback Machine cho trang thiếu ngày đăng/cập nhật"** — tắt mặc định. Khi bật: sau khi crawl xong, tool tự tra archive.org **chỉ cho những trang thiếu ngày** (tối đa 100 trang/lần), điền vào 2 cột ngày với nguồn ghi rõ "Wayback bản lưu đầu/cuối". Giao diện hiện tiến trình "Đang tra Wayback: x/y trang".

## ⚠️ Tình trạng hiện tại — nói thật

Code đã xong và push lên GitHub, **nhưng mình chưa xác nhận được kết quả thực tế**: phiên bản test đầu tiên gọi API song song quá nhanh khiến archive.org **chặn IP của bạn (lỗi 429)**, và lệnh chặn này kéo dài (thường 15–60 phút). ## Giải pháp — tùy site này là của ai

**Nếu là site của bạn / khách hàng của bạn (bạn có quyền quản trị):** đây là cách đúng và mất 2 phút:
1. Vào **Cloudflare Dashboard** → chọn domain → **Security → WAF → Custom rules**
2. Tạo rule **Skip** cho IP văn phòng của bạn (Expression: `ip.src eq <IP-của-bạn>` → Action: Skip → tick "All managed challenges")
3. Hoặc tạm thời hạ **Security Level** xuống "Essentially Off" trong lúc audit rồi bật lại

Sau đó tool (và Screaming Frog) quét bình thường. Đây cũng là cách các SEO agency chuyên nghiệp làm khi audit site khách.

**Nếu là site của người khác (đối thủ, tham khảo):** thì nên tôn trọng — chủ site đã chủ động khóa cửa với mọi crawler. Mình không hỗ trợ né tường lửa của site không thuộc quyền quản lý của bạn. Vài lối hợp lệ còn lại:
- Xem **bản lưu Wayback Machine** của site đó (web.archive.org — bot của Archive thường được Cloudflare cho qua)
- Dữ liệu Google đã index: search `site:dezignformat.com` để xem title/URL họ đang xếp hạng
- Xem thủ công bằng trình duyệt từng trang cần tham khảo

**Một điểm đáng ghi nếu bạn audit site này cho khách:** bật Managed Challenge cho *mọi* truy cập là con dao hai lưỡi SEO — Googlebot thật thì Cloudflare nhận diện và cho qua, nhưng các bot khác (Bing, Ahrefs, Facebook preview, Zalo link preview...) có thể bị chặn, ảnh hưởng hiển thị khi chia sẻ link và dữ liệu backlink. Đáng để khuyên khách nới rule cho "Verified bots".

## Các pattern mới đã thêm

2. **Thẻ `<time datetime>` có phân biệt nhãn**: text xung quanh chứa "Cập nhật/updated" → xếp vào **ngày cập nhật** thay vì ngày đăng (Dân Trí, Tuổi Trẻ hay hiển thị kiểu này)

## Từ chuỗi URL **đơn thuần** → KHÔNG thể

`ila.edu.vn/trai-nghiem-mua-he-mang-dam-tinh-giao-duc` — category (`tin-tuc`) **không nằm trong chuỗi này**. CMS khi cấu hình permalink dạng `%postname%` đã *cố tình bỏ* category khỏi URL. Thông tin đã bị lược đi thì không có phép biến đổi chuỗi nào lấy lại được. Không tool nào (kể cả Screaming Frog) "đoán" category chỉ từ ký tự URL.

## Nhưng **đọc lại từ trang/API** → CÓ, và mình vừa chứng minh

Category vẫn được website lưu ở chỗ khác, chỉ là không in vào URL. ILA chạy **WordPress**, mà WordPress có REST API trả về đúng category của mọi bài. Mình demo trên một site WordPress khác đang mở (wptavern.com) — đúng tình huống URL phẳng của bạn:

```
URL phẳng:  /patchstack-rejected-as-wordcamp-europe-2025-sponsor...
   ↓ gọi /wp-json/wp/v2/posts?slug=...
categories: [97, 4605]
   ↓ gọi /wp-json/wp/v2/categories/97
→ "News"  slug: news  →  tái tạo: domain/news/patchstack-rejected...
```

Vậy **tái tạo được `domain/%category%/%post%`** — nhưng bằng cách *truy vấn dữ liệu*, không phải sửa chuỗi.

## Các phương án, xếp theo độ tin cậy

| Phương án | Áp dụng | Độ tin cậy |
|---|---|---|
| **WordPress REST API** (`/wp-json/.../posts?slug=` → categories) | Site WordPress (ILA thuộc nhóm này) | Cao nhất — dữ liệu chính chủ |
| **Schema BreadcrumbList** (JSON-LD) | Site có breadcrumb chuẩn SEO | Cao |
| **Breadcrumb HTML** (`<nav class="breadcrumb">` "Trang chủ › Tin tức › …") | Đa số site có URL phẳng vẫn hiện breadcrumb | Khá |
| **meta `article:section`** | Vài plugin SEO xuất ra | Trung bình |

Vấn đề cốt lõi: **trang bài viết này KHÔNG công bố category ở bất kỳ đâu máy đọc được.** Mình kiểm tra đủ 4 nguồn của tool:

| Nguồn | Kết quả |
|---|---|
| Schema BreadcrumbList | ❌ không có (0 lần) |
| Breadcrumb HTML (class breadcrumb) | ❌ không có |
| meta article:section | ❌ không có |
| WordPress API | ❌ không phải WordPress |

Trang thậm chí **không có dòng breadcrumb "Trang chủ › Đồ lót › Bí quyết…"** nào. Không hề có nhãn "Danh mục: …" gắn với bài. Category của bài `n667` chỉ nằm trong **database của họ**, không được in ra HTML.

## Đã thử cả cách "vòng"

Mình thử tải trang danh mục `/do-lot-nc7.html` xem có liệt kê bài `n667` không để suy ngược ra — **kết quả: 0 lần xuất hiện**. Nghĩa là ngay cả cách đối chiếu chéo (crawl các trang danh mục rồi tìm bài) cũng không ăn, vì danh sách bài của họ render bằng JavaScript hoặc phân trang sâu.
